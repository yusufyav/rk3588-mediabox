### Gate MA1 - AC-3 / E-AC-3 transcoding and 6-channel LPCM
### VERDICT: NOT USABLE on this sink. Left disabled. Separate fault domain, not MA1's.

This was not part of the gate's passthrough scope - the brief keeps ac3transcode false
during codec tests precisely so a transcode cannot be mistaken for a real source codec.
It was measured because the operator asked for an AC-3 fallback for DTS titles, which
the sink cannot play. It is recorded here so the negative result is not re-derived later.

How Kodi chooses the transcode target (xbmc/cores/AudioEngine/Engines/ActiveAE/ActiveAE.cpp)
  The transcode branch is entered only when channels <= AE_CH_LAYOUT_2_0, passthrough,
  ac3passthrough and ac3transcode are all true and the source has more than 2 channels.
  It then sets STREAM_TYPE_EAC3 and falls back to STREAM_TYPE_AC3 only if eac3passthrough
  is false or the sink rejects E-AC-3:
      format.m_streamInfo.m_type = CAEStreamInfo::STREAM_TYPE_EAC3;
      if (!settings.eac3passthrough || !m_sink.SupportsFormat(...))
        format.m_streamInfo.m_type = CAEStreamInfo::STREAM_TYPE_AC3;

Attempt 1 - DTS source, channels 2.0, ac3transcode on, eac3passthrough on
  CAEEncoderFFmpeg::Initialize - EAC3 encoder ready
  MP2ALSA open:request ... passthrough=1 rate=192000 aeformat=3 AES0=0x06 AES3=0x0e
  ALSA RUNNING, zero errors.                      Operator at the TV: noise.

Attempt 2 - same, eac3passthrough off so the AC-3 encoder is chosen instead
  CAEEncoderFFmpeg::Initialize - AC3 encoder ready
  MP2ALSA open:request ... passthrough=1 rate=48000 aeformat=3 AES0=0x06 AES3=0x02
  ALSA RUNNING, zero errors, ActiveAE::SyncStream settling below its 30 threshold,
  player advancing normally at speed 1.           Operator at the TV: silence.

  Attempt 2's sink configuration is byte-for-byte the one that plays a real AC-3 file:
  same device, same 48 kHz S16_LE stereo carrier, same AES0=0x06. The only difference
  is that the burst payload is Kodi's own encoder output rather than the file's frames.
  That points at Kodi's encoder/IEC61937 packing, above the ALSA and kernel layers this
  gate proved. It is a real fault domain but a different one, and nothing about it was
  established well enough here to justify a patch.

Also measured - 6-channel LPCM, channels 5.1
  With audiooutput.channels = AE_CH_LAYOUT_5_1 (8), Kodi does not transcode at all: it
  decodes DTS and sends 6-channel LPCM, which the ELD declares (SAD1, LPCM 6ch).
      MP2ALSA open:request ... passthrough=0 rate=48000 channels=6 aeformat=24 AES0=0x04
      GetChannelLayout - Input 6 / Output 6, Requested Layout: FL, FR, FC, LFE, SL, SR
      ALSA RUNNING, zero errors.                  Operator at the TV: silence.
  So the profile stays at 2.0. This sink declares 6ch LPCM and does not reproduce it,
  the same way it declares DTS and does not reproduce it.

Sink-state control
  After all of the above, E-AC-3 passthrough was played again for 3.5 minutes and was
  clean at the TV. The sink had not latched into a mute state part-way through, so the
  three silent results above are genuine and not an artefact of test ordering.

Net effect on the profile
  ac3transcode false, channels 2.0. A DTS title is decoded and downmixed to 2.0 PCM,
  which this sink does play, instead of being re-encoded into something it does not.
