Kodi + libmali GBM buffer leak - root cause and fix
date: 2026-09-10T09:47:21+03:00

SYMPTOM
  Kodi starts on hardware Mali, renders, and then dies within 20-180 s:
    stdout : terminate called after throwing an instance of 'std::runtime_error'
             what():  eglSwapBuffers failed
    kodi.log: error <general>: eglSwapBuffers failed (EGL_BAD_ALLOC)
    kodi.log: libmicrohttpd: Error accepting connection: Too many open files
    dmesg   : [drm:rockchip_gem_iommu_map] *ERROR* out of I/O virtual memory: -28
              [drm:rockchip_gem_prime_import_sg_table] *ERROR* failed to import sg table: -28

MEASUREMENT THAT NARROWED IT (before the fix)
  Sampling /proc/<kodi>/fd and the rockchip DRM IOVA arena every 5 s:
    t=+5s   fds=3    used 39321600
    t=+10s  fds=543  used 4045516800
    t=+15s  fds=569  used 4294348800   <- arena is 4294967296, i.e. full
    t=+40s  KODI DEAD
  fd histogram at t=+10s: 513 of them are /dmabuf, every one exactly
  3686400 bytes = 1280x720x4, which is Kodi's own 'GUI format 1280x720'.
  So: one whole GUI-sized scanout buffer allocated per frame, never freed.

WHAT IT IS NOT
  1. Not a libmali GBM leak. tools swaploop.c does 200 swaps with the
     documented lock/release pairing:
       Mesa : 2 distinct bos, IOVA flat
       Mali : 2 distinct bos, IOVA flat
  2. Not a broken per-bo user-data cache. Kodi caches one DRM framebuffer
     per gbm_bo via gbm_bo_set_user_data (DRMUtils.cpp, DrmFbGetFromBo);
     userdata.c shows both stacks store and return it (10 hits / 2 misses).

ROOT CAUSE
  Kodi CGBMUtils::CGBMDevice::CGBMSurface::LockFrontBuffer() pushes a new
  locked front buffer every frame and releases the oldest ONLY when
  gbm_surface_has_free_buffers() reports the pool exhausted. That
  predicate is its single release trigger. Upstream even notes it 'may
  vary across other implementations' -- ARM's libmali does not vary, it
  never reports full at all.

  hasfree.c reproduces Kodi's exact algorithm at Kodi's exact GUI size:

    MESA  renderer            : llvmpipe (LLVM 19.1.7, 128 bits)
    MESA  surface             : 1280x720 (Kodi GUI format)
    MESA  frame 10   has_free_buffers=0  queue_depth=3
    MESA  frame 30   has_free_buffers=0  queue_depth=3
    MESA  frame 60   has_free_buffers=0  queue_depth=3
    MESA  frame 120  has_free_buffers=0  queue_depth=3
    MESA  first has_free_buffers()==0 at frame : see below
    MESA                                        4
    MESA  max queue depth     : 3
    MESA  VERDICT             : bounded - Kodi releases and the pool stabilises

    MALI  arm_release_ver: g24p0-00eac0, rk_so_ver: 10
    MALI  renderer            : Mali-G610
    MALI  surface             : 1280x720 (Kodi GUI format)
    MALI  frame 10   has_free_buffers=1  queue_depth=10
    MALI  frame 30   has_free_buffers=1  queue_depth=30
    MALI  frame 60   has_free_buffers=1  queue_depth=60
    MALI  frame 120  has_free_buffers=1  queue_depth=120
    MALI  first has_free_buffers()==0 at frame : NEVER
    MALI  max queue depth     : 120
    MALI  VERDICT             : UNBOUNDED - Kodi never releases; one buffer leaked per frame

  Mesa converges to three locked buffers at frame 4 and stays there.
  Mali's has_free_buffers() returns 1 forever, so the queue depth equals
  the frame count. At ~60 fps that is 3.6864 MB of display IOVA per frame,
  and the 4 GiB arena is gone in about eight seconds. The failure then
  surfaces as EGL_BAD_ALLOC from eglSwapBuffers, which Kodi turns into an
  unhandled std::runtime_error -- nothing in that chain points at the
  buffer queue, which is why it reads as a Mali incompatibility.

FIX (patches/kodi/0003)
  Bound the queue a second way that needs no cooperation from the GBM
  implementation: keep the has_free_buffers() release exactly as it is,
  and additionally pop when more than MAX_LOCKED_BUFFERS (4) are held.
  Mesa never reaches that cap, so its behaviour is bit-for-bit unchanged.

AFTER THE FIX - same run, DEFAULT fd limit (1024), not raised
  kodi pid           : 33468
  RLIMIT_NOFILE      : 1024 (soft, untouched)
  open fds           : 61
  of which dmabuf    : 5
  DRM IOVA arena     : total: 4294967296, used 57753600 free 4237213696
  iommu -28 errors   : 0
  Kodi buffer log    : 2026-09-10 09:45:15.758 T:33468   debug <general>: CGBMUtils - using 5 buffers (surface never reports full; bounded by Kodi)
  process alive      : yes
  JSON-RPC           : {"id":1,"jsonrpc":"2.0","result":"pong"}

  513 dmabufs -> 5. 4.29 GB of IOVA -> 57.7 MB, flat. No fd limit was
  raised to get this; raising it to 65536 earlier did NOT prevent the
  crash, because the binding constraint was the IOMMU arena, not the fd
  table. The fd exhaustion was a second symptom of the same leak.
